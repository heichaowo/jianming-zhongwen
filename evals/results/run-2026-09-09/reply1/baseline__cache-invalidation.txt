这是典型的缓存过期时间设置问题，具体原因和修法：

**为什么会有旧价格**

- 改价格时程序只更新了数据库，没有同步删除/更新 Redis 里对应的缓存 key。
- Redis 里该 key 设置了 TTL（比如 10 分钟），在过期前一直命中缓存，返回的是缓存写入那一刻的旧值。
- "最多 10 分钟"正好对应 TTL：最坏情况是价格刚改完、缓存刚写入就变价，用户要等满一个 TTL 周期缓存才会自然过期重新回源。

**怎么修**

1. **写时失效（推荐，优先做）**
   改价格的事务/接口里，更新数据库后立即 `DEL` 对应 key（或直接 `SET` 成新值）。这样不用等 TTL，改完立刻生效。
   ```
   UPDATE product SET price = ? WHERE id = ?;
   redis.del(f"product:price:{id}")
   ```
   注意顺序：先更新数据库，再删缓存（Cache-Aside 标准做法），避免并发读把旧值又写回缓存。

2. **缩短 TTL 作为兜底**
   删缓存这步万一漏了（比如批量改价、运营后台直接改库），TTL 是最后一道防线。价格类数据 TTL 建议缩到分钟甚至秒级，而不是靠 10 分钟兜底。

3. **如果是批量/后台直接改库（跳过业务代码）**
   要么让改价的入口统一收敛到一个服务（禁止绕过缓存失效逻辑直接写库），要么用数据库 binlog（如 Canal/Debezium）监听变更，自动同步失效 Redis，防止有人绕开代码直接改库导致缓存不一致。

4. **并发场景注意"删缓存失败"**
   `DEL` 操作本身也可能失败或消息丢失，重要数据建议加重试机制，或用延迟双删（更新库→删缓存→延迟几百毫秒再删一次）应对并发读写造成的脏写。

**根本原因一句话**：缓存和数据库是两份数据，改价格只改了一份，靠 TTL 被动过期而不是主动失效，所以用户会看到最长一个 TTL 周期的旧数据。
