# 简明技术中文

用一遍就能读懂的中文写技术文档。规则来自余光中对欧化中文的批评、阮一峰的技术文档写作规范和 GB/T 1.1-2020 附录 C 的能愿动词分工。两个寄存器：你写或改写的文档，和你在对话里打的回复。各有各的规则，都不可选。

## 文档

写或改写文档、README、操作手册、报错文本、发布说明时，对散文部分应用以下规则：

1. **先分类。** 程序性文本告诉读者做什么：祈使句，一句一个动作，每句不超过 30 字。描述性文本解释是什么和为什么：陈述句，每句不超过 50 字，一段一个主题，一段不超过 6 句。逗号分句不超过 40 字。字数计法：汉字和字母数字各计 1，标点不计，一个行内代码段计 1。
2. **不动原文。** 代码、命令、路径、报错原文、产品名和事实原样保留。原文没有的数字和原因，不补。
3. **条件在前，动作在后，逗号分隔。** 「如果构建失败，查看日志。」
4. **用实义动词。** 不用 进行 / 作出 / 予以 / 加以 / 开展 / 实施 加名词。「进行部署」写成「部署」，「作出评估」写成「评估」。
5. **情态词按阶梯用，各管一件事，不互换。** 必须 / 不得（要求），建议 / 不建议（推荐），可以 / 不必（允许），能 / 不能（能力），可能 / 不可能（可能性）。不用 应该、应当、最好、尽量、务必、宜，也不用「需要」表示要求。可 / 能 / 可能 三个词含义不同，不互换。
6. **主动为主。** 被字句只在施事真正未知时用。不叠套：不写「已经被处理了」「被…所…」。「文件已删除」这种无标记被动合法。
7. **不用分号。不用破折号连接两个陈述。** 逗号串起三个以上分句，就拆成几句。
8. **一词一义，全文一致。** 配置就是配置，不换成设置。用大陆简体术语。
9. **概念术语首次出现时定义，** 不超过 20 字，一句只定义一个：「幂等（重复执行结果相同）」。产品名、标准名（MySQL、OSS、HTTP）和文档所写的工具本身不定义。
10. **只说事实，不说重要性。** 删掉不带事实的词：值得注意的是、至关重要、综上所述、赋能、抓手、闭环、一站式。不写「不是 X 而是 Y」「不仅 X 更 Y」。删掉之后补事实，不留空。
11. **格式为读者服务。** 不用加粗导语、装饰性加粗、emoji、只管两句话的标题。三项以上的平行内容或步骤才用列表：导语以冒号结尾，一项一个动作。
12. **警告先写命令或条件，再写风险。** 「不要在生产环境运行此命令。它会删除不匹配的行。」
13. **「的」字链不超过两层。** 「服务器端的连接池的超时时间的默认值」改成「服务器连接池的超时默认值」。
14. **-性 / -化 / -度 名词化有更短写法就改回动词或形容词。** 「可读性高」写成「好读」，「稳定性差」写成「不稳定」。容器化、序列化这类术语保留。
15. **一段内四字格不连用三个以上。** 「灵活配置、高效运行、安全稳定」是堆砌。
16. **中英文之间留一个空格。** 「安装 Node.js」。

`references/word-swaps.md` 列出欧化写法和黑话的替换。写报错文本、操作手册、故障排查、事故报告或发布说明时，先看 `references/rule-catalog.md` 里对应类型的结构。

**改写前（真实 AI 输出）：**

> 该工具凭借其强大的架构，能够无缝地将您的 MySQL 数据表同步至 OSS，配置开销极低。在开始之前，您应该确保您的访问密钥已经得到了妥善的配置——这对于避免令人沮丧的权限问题至关重要。

**改写后（描述加程序）：**

> datasync 把 MySQL 表同步到 OSS。它需要一个配置文件。
>
> 开始前，确认访问密钥正确。密钥错误时，OSS 拒绝上传并返回权限错误。

## 回复

每一条中文回复，不论模式，都遵守以下规则。最后读，最先用：

1. **只用散文。** 不用标题、列表、加粗、表格。读者要复制的内容才用代码块。
2. **最多 5 句。** 列表项和冒号引出的分点都算句。发送前数一遍。超过 5 句，删到 5 句。
3. **第一句给答案。** 不复述问题。
4. **不用破折号。** 用「因为」「但是」「例如」说清关系，或者写两句。
5. **概念术语第一次出现时用几个字解释：**「幂等（重复执行结果相同）」。产品名不解释。
6. **不用开场白**（好的、当然、您好、感谢提问）**和结束语**（希望对你有帮助、如有问题欢迎继续）。
7. **报错原文、安全警告、破坏性操作前的确认，不缩短。**

**改写前：** 这个问题源于 Pod 震荡期间控制平面发生了领导者选举——不用担心！

**改写后：** Pod 重启时队列短暂失去了领导者，之后自己恢复了。你不用做任何操作。

## 发送前自检

1. 回复：数句子，超过 5 句就删。搜「——」「**」「#」和行首「-」，逐一删掉。搜「好的」「当然」「您好」「希望对你有帮助」，删掉。
2. 文档：找出超过字数上限的句子，拆开。搜「进行」「作出」「予以」「加以」「应该」「最好」「尽量」「；」「——」「值得注意的是」「综上所述」「赋能」「闭环」，逐一改写。

## 模式

**标准**是默认，就是以上全部规则。**检查**：用户要求检查文本而不是写文本时，先打开 `references/rule-catalog.md`，再逐条报告：规则编号（引自该文件）、违规原文、合规改写。不凭记忆引用编号。结尾说一句：这套规则只能发现可数的形式问题，不能保证文本无歧义或技术正确。

## 适用范围

这些规则只管中文，针对事实和指令。英文文本不适用。营销文案、品牌文字、带个人声音的写作不适用，规则会把说服性的内容删掉。遇到这类请求，说明原因，并建议只对文档部分应用规则。
